1. What this is

apps/web/public/v2_plan.html is the v2 plan deliverable, submitted during v1 week, and nothing here replaces or contradicts it: this is the build plan, the order the work actually happens in, revised in light of the TA and peer feedback that arrived after that plan was written.

Where the two documents touch, the submitted plan is the authority on what and this one is the authority on when. Live, at recipes-tan-nine.vercel.app, source at github.com/mrajesh164/recipes.

2. The judgement that sets the order

The feedback is overwhelmingly about coherence, not features.

Of the ten points the TA made, seven are about hierarchy, scatter, and not knowing where to look: the name appearing twice, the actions getting lost in the saved view, icons needing a normalization pass, the UI feeling scattered, texture applied everywhere instead of in places, being confused about where to look, and the instruction to arrange everything better. One more, the width changing after you search, is about the interface feeling unsturdy. One is an affordance that does not exist yet, the square with an arrow for a link that leaves the site. Exactly one is a feature request: that the search box should recognise anything.

7 of 10TA points are about hierarchy, scatter, or not knowing where to look. One is a feature request.
2places the app renders its own name: layout.tsx:51 and page.tsx:17.
1inline <svg> in the entire app, a bookmark glyph. Three outbound links, no external mark.
1 linescrollbar-gutter: stable on html is the whole fix for the reported width jump.

So v2 leads with a design pass and the feature requests queue behind it. The reasoning is not sequencing for its own sake: adding a pantry filter to a scattered interface makes a scattered interface with a pantry filter. Every feature in section 6 puts at least one more control on a surface that three separate people have now said is hard to read. Deciding where controls live is a precondition for adding any.

It also happens that this is the graded surface. Design is the focus for this project and is held to a higher standard than the rest, so the thing the feedback is complaining about is the thing being marked.

3. The feedback

From the TA

  • Rethink the hierarchy in the visual layout. The Perfect Batch appears twice.
  • The screen width changes after you type and search, which makes the interface feel unsturdy.
  • The saved-recipe view needs work. The lines with dots are confusing, and Open recipe and Save get lost and are hard to find.
  • Do a normalization pass on icons and interaction elements.
  • Use a square with an arrow for Open recipe, because it takes the user off the site.
  • The UI feels scattered. Clean it up.
  • Arrange everything better.
  • Maybe a white background, with sprinkles and texture confined to certain areas.
  • It is confusing where to look.
  • Ideally the search box recognises anything. When it does not, that could be a delightful or surprising moment, or it could suggest alternatives and near-match recipes.

From peers

  • A pantry or ingredients filter.
  • How long a recipe takes.
  • Recording feedback after trying a recipe: liked, or did not like.
  • Personal information and allergies.
  • Choosing from several recipe results rather than one.

Mine, wanted in v1 and not done

  • GitHub issues as the unit of work.
  • Continuous integration.
  • Pull requests rather than pushes to main.
  • Subagents reviewing pull requests.

4. Faults carried over from v1

Known, still open, and each one now has a slice that owns it.

Mislabelled recipesA few recipes in the corpus are not the dish they were filed under, which widens every range they sit in. Slice 4.
Oats are not flourOats are not counted as flour, so oatmeal recipes read as fattier than they are, across all 73 of them. Slice 4.
Negation dropped“Not cakey” is reported as not understood rather than used, which is a dead end for a reasonable request. Slice 5.
PayloadRoughly 1.1 MB of recipe JSON is serialized into every page load, and it grows with the corpus. Slice 1 if it is one serialization boundary, its own issue if not.
Why the first two belong to the plot slice and not to a maths slice. The submitted plan already makes this argument and it still holds: the plots present a wrong number with exactly the same confidence as a right one, so the interface is quietly vouching for something it has not earned. Fixing the readability of a plot that is showing the wrong figure is the wrong order of operations.

5. Build plan

Eight slices. Each is something that can be deployed and looked at, which is the same unit PLAN.md section 7 already uses. Deploy after every slice.

Slice 0

before any of the work

0 Set the workflow up first mine done

Where it got to. CI runs the secret scan, the typecheck and the tests on every push and pull request, and is green. Issue and pull request templates are in. Agent review is a step in the pull request template, run locally rather than as a paid CI action.

GitHub issues as the unit of work, one per slice. A GitHub Actions workflow running on every pull request. Pull requests rather than pushes to main. An agent review on each pull request before it merges.

Why this is first and not last. Retrofitting it after the work gains nothing. Issues written after the fact are documentation, not a unit of work, and a pipeline added at the end has never caught anything. Put it in before slice 1 and the seven slices that follow all flow through it, which means the process is demonstrated rather than described.

The CI config is already written. .githooks/pre-push runs a credential-shape scan and a typecheck today. The Actions workflow transcribes those two steps and adds the 132 tests. This is a transcription of checks that already exist, not an invention, which is most of why it is a cheap first slice rather than an expensive one.

Done when every slice below arrived as a pull request that closes an issue, with CI green and an agent review on the diff.

Slices 1 to 4

the design pass, where the grade is

1 The cheap structural fixes TA two of three

Where it got to. scrollbar-gutter stops the layout shifting when results appear. All three outbound links carry a square-with-arrow. The duplicated title is deliberately still open: it is a decision about the header, and the header is better decided with the rest of the layout.

Roughly a day. Three reported complaints, each with a one-line cause.

  • The name twice. “The Perfect Batch” renders as the header logo at apps/web/src/app/layout.tsx:51 and again as the page <h1> at apps/web/src/app/page.tsx:17. This slice ends the duplication. Slice 3 decides what the surviving line says.
  • The width jump. globals.css sets no scrollbar-gutter. Results make the page taller than the viewport, a scrollbar appears, and the layout shifts sideways by its width. That is exactly the unsturdiness reported. scrollbar-gutter: stable on html is the whole fix.
  • The external-link mark. Three target="_blank" links carry no affordance at all. Add the square with an arrow. It is the first icon in the set slice 2 defines, so it gets drawn to that spec rather than pulled from somewhere.

No design problem here, which is the reason these go first. Nothing in this slice needs a judgement call, and two of the three TA complaints about sturdiness and affordance close on the first day.

2 A design system, written down TA three of four

Where it got to. Seven-step type scale, with all three page titles unified at one size. One icon source with a shared geometry. The texture is off every working surface and lives in the header band only. The spacing and radii scale is the piece still open.

This is the TA’s “normalize the icons” and “white background, texture only in certain areas” taken as one job, because they are one job: both are rules about what the surface is allowed to do.

  • A type scale and a spacing scale, as custom properties, with a fixed number of steps, so that a later slice cannot invent a fourteenth size.
  • One icon set at one stroke weight. The whole app currently contains one inline <svg>, a bookmark glyph. There is no icon system to normalize: there is nothing. So the pass means drawing the set, not auditing one.
  • Surface rules, stated. What is paper, meaning the white working surface. What is cream. What is patterned.
  • The sprinkles get zones. The texture is a repeating SVG data URI applied to body, so it sits behind everything on every page. Confining it means moving it off body onto named containers: the header band, empty states, the signed-out page. The working surface goes white.

Design problem: the texture is most of what gives this app a character, so taking it off body risks replacing a scattered app with a forgettable one. The rule has to say where the pattern is required, not only where it is banned.

3 A hierarchy pass on the three views TA three of four

Where it got to. One shared action row in the same position on all four recipe surfaces. Browse names its sort order and lets it be changed. Saved is rebuilt as rows with the action in a fixed footer. The title decision is the same one carried over from slice 1.

Home and recommendation, saved, browse. For each view, name the one primary thing, then place the actions consistently and in the same spot across all three. This is the answer to “it is confusing where to look” and to “Open recipe gets lost”.

  • Home. The recommendation is primary, the reasons panel is second, and the free-text box keeps the front door. The submitted plan already settled that last point and it is not reopened here.
  • Saved. Each saved recipe gets one obvious primary action in a fixed position, rather than a row of equal-weight links that the eye has to sort through. This is where the TA said things get lost, and it is the view with the least design attention in v1.
  • Browse. A list of 325 is not useful until it says what it is sorted by.

The duplicated title, decided. Two options. Either the <h1> goes and the header logo carries the name alone, or the <h1> stops repeating the name and becomes the actual proposition, what the app will do for you. Preference: the second. The header carries identity and the <h1> carries the offer. Repeating the name spends the largest type on the screen saying nothing.

Design problem: “arrange everything better” is not actionable until each view has one stated primary. The deliverable of this slice is that sentence, per view, written into the repo, so every later placement decision can be checked against it instead of argued about.

4 Make the plots readable TA done, and live

Where it got to. Four attempts: dots, then a histogram, then a position track, then the wording. What shipped is the ratio and its value on one line, a track filled to where it sits, and one sentence counted in tenths. One ratio leads and the other two are a click away.

The TA says the lines with dots are confusing. This is the hardest item on the list, and it is hard for an uncomfortable reason: the dot plots are the best idea in the product and they are apparently not reading. The evidence panel is the whole difference between this and a search engine, so if it does not land, the thing that makes the app worth building does not land.

Options worth naming, roughly cheapest first. One or two of them, not all five.

  • Fewer dots. A hundred and fifty-seven points on one axis is a smear, not a comparison.
  • Binning, so the shape of the corpus is visible instead of every member of it.
  • A clearer axis, with a unit and a direction, so the reader is not inferring both.
  • Label the extremes, so the ends of the line mean something without a legend.
  • Position in words, beside the plot. “More butter than four in five chocolate chip recipes.” It is worth entertaining that the sentence does most of the work and the plot is the garnish.

The two accuracy faults from section 4 land here, because a readable plot showing a wrong number is worse than an unreadable one.

Design problem: the plot has to answer “why this one” at a glance, and it currently asks the reader to decode an axis before it pays anything back. Whichever option wins has to require nothing to be learned first.

Slices 5 to 6

after the surface is coherent

5 A search box that recognises anything TA two of three

Where it got to. Three tiers, each running only when the one before it finds nothing: the keyword matcher, a misspelling check, and a 22 MB embedding model that runs in the browser and is only fetched when a word is genuinely unknown. An unknown word is read as the nearest phrase the vocabulary already knows and inherits its weights, so nothing new is scored. Above 0.60 it is applied and shown as "read stodgy as fudgy"; between 0.40 and 0.60 it is offered as a question with the nearest three as buttons, which is what turned "I couldn't read anything in that" into something you can act on. Acting on negation rather than dropping it is the piece still open.

Three parts, in this order.

  • Widen the vocabulary. v1 reports what it dropped, which is honest, but being told a word was ignored is not the same as being understood.
  • Act on negation instead of dropping it. Rank away from a texture, not only toward one. “Not cakey” is currently a reported dead end for a request any baker would consider reasonable.
  • Design the no-match case properly. The TA offered two shapes for it: a delightful or surprising moment, or suggested alternatives and near-match recipes. Probably both. The near match is the useful half, and the moment is what keeps a dead end from reading as a failure.

All of this extends the honesty loop that already exists rather than replacing it.

you typed: not cakey, nutty oat

Today: reading that as oat.

“Not cakey” dropped. “Nutty” dropped. Two of three words discarded, both reported honestly, and the result is a recommendation the person did not ask for.

After slice 5, the same phrase should rank away from cakey, offer a near match for nutty, and still say plainly what it did with each word. The loop stays, it just stops being a terminus.

Design problem: “recognises anything” and “says honestly what it failed to understand” pull against each other, and a box that silently guesses is worse than one that admits a gap. The target is a box that always returns something and always says what it did with your words.

6 The feature requests peers not started

Held until slices 2 and 3 have said where controls live, because each of these adds a control to the surface the feedback already calls scattered.

Pantry and ingredientsAlready in the submitted plan as “Tell it what you have”, first in its Add next band. Peers arrived at it independently. That convergence is the useful signal here: the strongest unprompted request is also the one already planned, so it leads this slice.
From what you savedAlso already in the submitted plan. Saves already store the words typed when the recipe was kept, so the signal exists and is unused.
Time to makeNew, from peers. bake_minutes and chills_dough are already columns, so this is mostly a display decision.
Several resultsNew. It is in tension with v1’s premise, which is removing the deciding. More likely the runners-up become visible than the answer becomes a list of five.
Post-bake feedbackNew. Liked, or did not like. Every table today is public-read and nobody-writes, so this is the first real write surface after saves and carries the RLS work with it.
AllergiesNew. Mechanically the same shape as the pantry filter: both are constraints on candidates. Probably one filter with two labels, not two systems.

The submitted plan’s texture slider and other baked goods sit in this band too and keep their stated place in it.

Design problem: six requests, and the honest version of this slice ships two or three of them well rather than all six thinly. The pantry filter and the saved-set recommendation are the two with a design problem already worked out in the submitted plan, so they go first.

Slice 7

parked

7 Live search beyond the corpus mine parked

Searching the web at request time rather than a fixed set of 325. Parked, unchanged from the submitted plan.

What it would cost: every number in this app rests on 94% of ingredient lines converting to grams, 3,396 of 3,632, over a corpus that was harvested and checked. Trusting an arbitrary page’s structured data at request time gives that up, and a recommendation with unverified measurements behind it is worse than a smaller library.
